[2편]({{ '/posts/agentic-bsp-shift-five-pillars/' | relative_url }})에서 공통 계약을 정의했습니다. 이제 범위가 작고 재현 가능한 호스트 업무 하나에 적용합니다. 목표는 모델이 패치를 만드는 데서 끝나지 않고 **오류 재현 → 조사 → 수정 → 독립 검증 → 결과 기록**을 이어가는 것입니다.

이 글의 Phase 1은 호스트 작업 범위를 뜻합니다. L2를 건너뛰어 더 높은 점수에 도달하는 과정이 아닙니다. 저장소 조사·패치 생성·도구 실행 능력을 한 과제의 완료 조건에 맞춰 결합합니다. 아래 절차는 파일럿 설계이며 실제 실행 성과는 아직 측정하지 않았습니다.

## 1. 시작 전: 현재 방식과 평가 과제를 고정한다

첫 후보는 빌드 오류 수정입니다. 과거 이슈에서 재현 가능한 사례를 고르고, 개인정보·독점 자료의 사용 범위를 확인합니다. 이미 해결법을 프롬프트나 Skill 작성에 사용한 사례와 최종 평가 사례를 분리합니다.

| 실행 전 고정 항목 | 내용 |
|---|---|
| 입력 | 실패 소스 manifest/commit, 타깃 설정·툴체인, 실패 로그 |
| 현재 방식 A | 엔지니어가 실제로 쓰는 스크립트·검색·기존 AI 도구와 검토 절차 |
| 에이전트 방식 C | 같은 입력·환경·완료 기준에 Profile·Skill·검증자를 추가 |
| 완료 조건 | 재현된 오류 해소, 지정 타깃 빌드와 필수 검사 통과, 의미 변경 검토 |
| 실행 한도 | 재시도 횟수·시간·비용·수정 범위와 인계 조건 |

비교군 이름은 A(현재 방식), B(일반 코딩 에이전트), C(BSP 통합 흐름)로 통일합니다. 첫 파일럿은 A/C 비교로 시작할 수 있습니다. 기존 방식도 이미 자동 빌드 스크립트나 AI를 사용한다면 그대로 기준선에 포함합니다. 사람이 불편한 환경에서 작업한 시간과 잘 준비된 에이전트 환경을 비교하지 않습니다. 비교군 B를 추가해 하네스 효과를 분리하는 방법은 5편에서 설명합니다.

## 2. 작업 공간과 빌드 조건을 분리한다

전용 브랜치와 worktree에서 소스를 수정합니다. 아래는 단일 Git 저장소의 예이며, AOSP처럼 다중 저장소인 환경은 manifest 고정과 프로젝트별 작업 공간 정책이 추가로 필요합니다.

```bash
git worktree add .worktrees/agent-build-fix -b fix/compiler-error
```

Worktree는 소스 체크아웃을 분리합니다. 공유 출력 경로·Bazel 캐시·잠금 파일·백그라운드 데몬·호스트 자원까지 격리하지는 않습니다. 프로젝트가 지원하는 출력 경로와 자원 한도를 지정하고 동시 실행 간섭을 확인합니다.

빌드는 저장소가 실제로 사용하는 wrapper와 타깃을 Profile에 등록합니다. Kleaf/AOSP/벤더 커널의 명령을 모델이 이름만 보고 추측하게 하지 않습니다. 생성된 `.config`, DT 선택, 툴체인과 산출물 해시를 기록해 같은 조건에서 실패를 재현했는지 확인합니다.

## 3. 첫 폐루프: 빌드 오류 수정

```text
고정된 입력에서 실패 재현
  ↓
에이전트: 오류·심볼·관련 설정 조사, 수정 가설과 최소 diff 생성
  ↓
정책 wrapper: 허용 파일·명령·자원 한도 확인 후 빌드
  ↓
독립 검증: 지정 빌드 + 변경 범위 검사 + 필수 테스트
  ├─ 통과: 검증 범위와 증거를 결과에 기록
  ├─ 실패: 한도 안에서 증거를 보고 다음 가설 시도
  └─ 판정 불가/한도 초과: diff·로그·다음 조사 항목을 보존해 인계
```

고정된 명령 순서를 실행하는 wrapper가 도구와 자원 제어를 담당합니다. 에이전트는 어떤 심볼·설정을 조사하고 어떤 패치를 시도할지 판단합니다. 검증자는 에이전트의 설명을 받아 점수를 주는 대신 사전 등록된 검사를 수행합니다.

컴파일러 오류가 사라져도 드라이버를 비활성화하거나 문제 코드를 삭제한 수정일 수 있습니다. diff에서 요구 기능·테스트·경고 정책·Kconfig·ABI에 영향을 주는 변경을 검토하고, 허용되지 않은 범위면 완료로 처리하지 않습니다. 호스트 검사만 했다면 결과도 **호스트 검증 통과**로 한정합니다.

## 4. 같은 계약을 적용할 두 가지 추가 과제

### DTS 문법·바인딩 검사

DTS 변경은 문법 검사와 바인딩 검사를 구분합니다. `dtc` 통과만으로 YAML 바인딩 준수까지 확인했다고 보고하지 않습니다. 해당 커널의 빌드 환경에서 변경한 DTS/바인딩에 맞는 검사 타깃을 사용하고 적용 범위·제외된 검사를 기록합니다.

Linux 문서는 바인딩 스키마 검사에 `dt_binding_check`, DT 산출물 검사에 `dtbs_check`를 설명합니다. 실제 프로젝트에서는 필요한 의존성과 wrapper 지원 여부를 확인한 뒤 호출합니다. 검사 통과가 실제 배선·전압·전원 시퀀스의 정확성을 증명하지는 않습니다. ([커널 바인딩 검사 문서](https://docs.kernel.org/devicetree/bindings/writing-schema.html))

### 저장된 Kernel Oops / Panic 분석

입력은 이미 수집된 덤프와 해당 빌드의 디버그 심볼입니다. 호스트에서 `vmlinux`와 필요 모듈 심볼을 확인하고 아키텍처에 맞게 주소를 해석합니다. KASLR·모듈 로드 주소·심볼 불일치를 처리할 정보가 없으면 소스 위치를 확정하지 않습니다.

이 과제의 산출물은 **심볼 매핑과 증거를 갖춘 원인 후보·다음 검증 계획**입니다. 패치를 배포해 문제가 사라졌다는 결과와 다릅니다. 진단 과제와 수정 과제의 완료율을 같은 분모로 합산하지 않습니다.

## 5. 실패를 숨기지 않는 인계 계약

한도에 도달하거나 입력을 재현하지 못하면 다음을 남깁니다.

- 입력과 실행 조건, 재현 성공 여부와 실패 명령.
- 시도한 가설·변경 diff·검사 결과와 원본 로그.
- 확인된 사실, 아직 입증하지 못한 가설, 다음에 필요한 정보.
- 사람이 이미 개입한 내용과 소요시간, 실행 비용.

사용자 변경과 실행 증거를 보존하기 전에 자동 `reset`이나 `clean`으로 작업을 지우지 않습니다. 인계 후 사람이 복구·수정한 시간도 같은 과제의 사람 투입시간에 포함합니다.

## 6. 파일럿의 산출물과 통과 기준

파일럿은 한 과제군에서 같은 입력·완료 기준으로 A와 C를 비교합니다. 사례 수는 먼저 절차를 점검할 수 있는 범위로 시작하되, 적은 사례의 결과를 전체 BSP 업무의 성공률로 일반화하지 않습니다. 비교 순서와 담당자의 숙련도·정답 학습 효과를 기록합니다.

| 지표 | 이 편에서 기록할 값 |
|---|---|
| 검증된 완료 | 전체 시도 중 사전 등록된 필수 검사를 통과한 실행 |
| 사람 투입시간 | 준비·프롬프팅·조사·승인·검토·수정·실패 후 복구의 활성 시간 |
| 전체 경과시간 | 큐·빌드·재시도·인계를 포함한 시간과 최종 상태 |
| 품질·비용 | 거짓 완료, 재작업, 호출·컴퓨팅 비용 |

성공 사례뿐 아니라 실패·시간 초과·판정 불가도 집계합니다. 필수 검사와 품질 조건을 유지하면서 사람 투입시간이나 전체 소요시간이 개선되는지 확인한 뒤 범위를 넓힙니다. 구체적인 계산과 비교 설계는 5편의 공통 규칙을 사용합니다.
