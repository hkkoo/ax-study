[제1편]({{ '/posts/agentic-bsp-shift-definition-and-landscape/' | relative_url }})에서 L1~L6 성숙도 모델을 정의하고, [제2편]({{ '/posts/agentic-bsp-shift-five-pillars/' | relative_url }})에서 자율 에이전트를 지탱하는 5대 아키텍처 기둥을 정립했습니다.

이제 가장 중요한 실전 질문으로 들어갑니다.
**"현재 코드 자동완성과 단순 질의응답(L1) 수준에 머물러 있는 우리 팀이, 어떻게 단계를 밟아 자율 엔지니어링으로 나아갈 것인가?"**

공상과학 같은 완전 자율(L6)을 처음부터 넘보는 것은 실패의 지름길입니다. 가장 효과적인 방법은 **단계별 마일스톤(Phase)**을 나누고, 현장에서 즉시 성과를 낼 수 있는 **Phase 1: L1 → L3~L4 도약**부터 정복하는 것입니다.

---

## 1. 현실 직시: L1의 한계와 Phase 1의 목표

### 1.1 L1에 머무르는 BSP의 일상
현재 많은 엔지니어들이 IDE의 코드 자동완성(Copilot)을 켜두거나, 챗봇 창에 C 문법을 물어보는 수준(L1)에는 익숙해졌습니다. 하지만 솔직하게 돌아보면, 이것이 BSP 개발의 실제 업무 시간을 줄여주고 있습니까?

BSP 엔지니어의 일주일 업무 중 순수하게 **'C 코드를 직접 타이핑하는 시간'은 5~10%에 불과**합니다. 나머지 90% 이상의 시간은 다음과 같은 고통스러운 작업에 쓰입니다:
- 수백 GB의 AOSP/커널 소스 트리에서 grep과 find로 핀맵, DT 매크로, 드라이버 소스 찾아 헤매기
- 30분 동안 돌아간 빌드가 에러 하나로 멈췄을 때, 수천 줄의 로그를 스크롤하며 include 누락이나 선언 충돌 찾기
- 커널 패닉(Oops)이 발생했을 때 16진수 레지스터와 스택 주소를 호스트 심볼과 대조하기

L1 수준의 도구는 이 거대한 빌드·진단 사이클을 전혀 대신해주지 못합니다. 여전히 엔지니어가 수동으로 로그를 복사해 붙여넣고, 고친 코드를 손수 빌드 명령어로 돌려봐야 합니다.

### 1.2 Phase 1의 핵심 목표: L2를 건너뛰고 L3~L4로 직행
단순 함수 생성 수준인 L2에 오래 머물 필요가 없습니다. Phase 1의 목표는 **"호스트 상의 소스 탐색(L3)과 빌드·정적 진단의 자율 폐루프(L4)"**를 완성하는 것입니다.

```text
[Phase 1의 Closed-Loop 범위]
이슈 발생 (컴파일 에러 / DT 오류 / Oops 로그)
  ↓
에이전트 자율 소스 탐색 (Target Profile & 저장소 맥락) ── [L3]
  ↓
패치 생성 및 적용
  ↓
에이전트가 직접 빌드 wrapper 실행 ───────────────────── [L4]
  ↓
빌드 성공 (exit code 0) 확인 시 완료 보고 ───────────── [L4]
(실패 시 로그 자동 재수집 후 스스로 수정 반복)
```

## 2. L3 달성 전략: 저장소 및 하드웨어 맥락 주입

에이전트가 수백 GB의 AOSP/커널을 한눈에 볼 수는 없습니다. 컨텍스트 윈도우 한계 내에서 에이전트에게 올바른 눈을 달아주는 전략이 필요합니다.

### 2.1 Target Profile 주입
[제2편]에서 강조한 하드웨어 스펙 파일입니다. 에이전트가 작업을 시작하기 전, 다음 정보를 프로필 형태로 명시적 주입합니다:
- 대상 SoC (예: Qualcomm, MediaTek, NXP 등) 및 보드 리비전
- 빌드 Entrypoint: 독립 `make`가 아닌 프로젝트 표준 빌드 wrapper (Kleaf `bazel build //common:kernel`, Android lunch 타깃)
- 커널 defconfig 경로 및 DT 소스 디렉터리 위치

### 2.2 Git Worktree 기반의 작업 격리 (Workspace Isolation)
엔지니어가 작업 중인 메인 저장소에서 에이전트가 직접 소스를 고치면 충돌이 발생합니다. Google의 워크스페이스 격리 원칙을 도입하여, 에이전트 전용 worktree를 분기합니다:

```bash
# 에이전트 전용 격리 작업 공간 생성
git worktree add .worktrees/agent-build-fix -b fix/compiler-error
```
에이전트는 이 격리 공간에서 마음껏 코드를 수정하고 시험 빌드를 돌릴 수 있으며, 메인 트리에 영향을 주지 않습니다.

## 3. L4 달성 전략: 호스트 빌드·정적 분석 폐루프 (3대 Quick-Win)

Phase 1에서 가장 먼저 에이전트에게 완전히 일임해야 할 **3대 자율 과제**입니다. 이 과제들은 하드웨어 장비(DUT)가 필요 없고 호스트 서버 안에서 완결되므로, 가장 안전하고 빠르게 ROI를 입증할 수 있습니다.

### ① Kleaf / AOSP 빌드 오류 트리아지 & 자동 복구
- **시작 조건**: 컴파일러 에러 로그 (gcc/clang error, linker undefined reference)
- **자율 절차**:
  1. 컴파일러 에러 로그에서 파일명, 라인 번호, 심볼명 파싱
  2. 대상 소스 파일 및 관련 헤더 탐색
  3. 시그니처 변경, 매크로 정의 누락, 헤더 include 누락 수정
  4. 격리 환경에서 빌드 wrapper 재실행
  5. exit code `0` 달성 시까지 제한된 횟수(예: 최대 3회) 내 자율 재시도

### ② Device Tree 문법 및 바인딩 사전 검사 루프
- **시작 조건**: DTS/DTSI 수정 요구 또는 문법 검증 요청
- **자율 절차**:
  1. 수십 분이 걸리는 전체 커널 빌드를 돌리기 전에, `dtc` 및 `dtschema` 검증 도구 직접 호출
  2. YAML 바인딩 규칙 위반(누락된 필수 속성, 잘못된 unit-address) 검출
  3. 에이전트가 DTS 수정 후 `dtc` 재검사 통과 확인

### ③ Kernel Oops / Panic 심볼 역추적
- **시작 조건**: 타깃 부팅 시 콘솔에 찍힌 Kernel Oops / Panic 덤프
- **자율 절차**:
  1. Oops 덤프에서 Crash PC, LR, Call Trace 레지스터 주소 파싱
  2. 호스트에 빌드된 `vmlinux` 심볼 파일과 `addr2line` 도구 호출
  3. 주소를 정확한 C 소스 코드 라인(`drivers/net/.../foo.c:142`)으로 변환하고 원인 코드 스니펫 제시

## 4. Phase 1의 안전성: 왜 위험이 없는가?

현장 엔지니어들이 에이전트 도입을 가장 두려워하는 이유는 "보드가 벽돌이 되거나(Brick), 메인 브랜치가 꼬일까 봐"입니다.

하지만 **Phase 1의 모든 작업은 철저하게 '호스트 상의 컴파일 및 정적 분석'에만 머뭅니다.**
- 물리 보드에 플래시(Flash)하지 않으므로 하드웨어 파손 위험이 **0%**입니다.
- Git worktree 격리 환경에서 돌기 때문에 엔지니어의 로컬 작업 트리가 오염되지 않습니다.
- 에이전트가 빌드에 성공하더라도, 최종 패치를 메인 브랜치에 머지하거나 Gerrit에 푸시하는 과정은 **엔지니어의 승인(Human Approval Gate)**을 반드시 거치도록 잠급니다.

즉, Phase 1은 **위험은 제로이면서, 엔지니어의 가장 지루한 빌드 에러 디버깅 시간을 즉시 덜어주는 최적의 출발점**입니다.

## 5. Phase 1 성공을 판정할 정량적 KPI

Phase 1이 성공적으로 현장에 안착했는지는 감(Feeling)이 아니라 다음 3가지 지표로 측정합니다:

| 측정 지표 | 목표 기준선 | 측정 방식 |
|---|---|---|
| **빌드 오류 자율 해결률**<br/>(Autonomous Fix Rate) | **80% 이상** | 사전에 준비한 컴파일/바인딩 오류 10건 중 에이전트가 사람 개입 없이 빌드 성공을 이끌어낸 비율 |
| **사람 투입시간 절감**<br/>(Human Touch Time) | **50% 이상 절감** | 동일한 빌드 오류 디버깅 시 엔지니어가 직접 개입한 활성 시간(Active minutes) 비교 |
| **거짓 완료율**<br/>(False Positive Rate) | **0%** | 빌드 리턴 코드 `exit 0` 및 diff 회귀 검사를 기계적으로 검증 |
