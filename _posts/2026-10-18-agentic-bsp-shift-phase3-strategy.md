[3편]({{ '/posts/agentic-bsp-shift-phase1-strategy/' | relative_url }})은 호스트 폐루프, [4편]({{ '/posts/agentic-bsp-shift-phase2-strategy/' | relative_url }})은 런타임 증거와 검증 범위를 다뤘습니다. 이제 반복 가능한 업무를 CI·장치 운영에 연결하고, 기존 방식보다 나아졌는지 평가합니다.

이 편의 Phase 3는 운영 범위의 확장입니다. CI, 실물 DUT, 다중 에이전트를 모두 갖춰야 성공하는 단계는 아닙니다. **한 업무에서 품질 조건을 유지하며 사람 투입시간과 총비용을 개선했다면 그 범위의 성과로 기록합니다.** 아래는 운영·실험 설계이며 측정된 ROI 결과는 아닙니다.

## 1. 고정된 자동화와 에이전트의 판단을 구분한다

빌드·수집·검증·장치 제어는 가능한 한 등록된 도구와 정책이 수행합니다. 에이전트는 증상에 맞는 조사·가설·패치를 선택하고, 검증 결과로 다음 행동을 결정합니다.

```text
이슈 / CI patchset
       ↓
실행 관리자: 입력·정책·예산·타깃 고정
       ↓
에이전트: 조사 → 가설 → 허용된 도구/패치 선택
       ↓
실행 도구: 빌드·관측·승인된 배포 / 독립 검증자: 판정
       ↓
증거 리포트·KPI 기록 → 승인된 피드백 또는 사람 인계
```

기존 CI가 동일한 고정 시험을 이미 수행한다면 그 능력을 기준선에 포함합니다. 단순 CI 호출 횟수나 에이전트 수 증가를 자율성의 성과로 세지 않습니다.

## 2. 실물 DUT는 필요한 작업부터 제한된 범위로 연결한다

실제 주변장치·전원·열·신호를 다루는 과제에는 실물 DUT와 필요한 계측이 필요합니다. 먼저 한 보드의 읽기 전용 관측부터 연결하고, 상태 변경은 복구 절차와 정책이 검증된 범위로 확대합니다. 대규모 보드 팜 구축이 출발 조건은 아닙니다.

| 운영 계약 | 구현·확인할 내용 |
|---|---|
| 타깃 식별 | 보드 리비전·연결 경로·장치 ID와 실제 대상 확인 |
| 단일 점유 | 보드 예약, 소유권·만료·연장, 이전 소유자의 늦은 명령 차단 |
| 관측 | UART·부팅 세션·원본 보존, 전원 변경 전후의 로그 연결 |
| 상태 제어 | 보드별 리셋·전원·부팅 모드 제어와 허용 조건 |
| 배포 | 소스·이미지 해시·대상·슬롯·서명/잠금 상태·승인 범위 확인 |
| 복구·격리 | 검증된 복구 경로, 횟수·시간 한도, 실패 시 보드 사용 중단과 사람 인계 |

락은 점유 토큰 발급만으로 끝나지 않습니다. 장치 제어 계층이 현재 소유권을 검사해 오래된 프로세스의 명령도 거부해야 합니다. 한 실행이 끝나기 전에 다른 실행이 같은 DUT를 재설정하지 않도록 합니다.

전원 차단 시간이나 비상 모드 진입 방법은 보드 문서와 실험으로 정합니다. UART 핀 조작이나 USB 전원 단속만으로 모든 SoC의 EDL·Maskrom·BROM 진입이 가능하다고 가정하지 않습니다. 복구가 실패하면 무한 재시도하지 않고 로그와 장치 상태를 보존해 인계합니다.

## 3. 파티션 이름으로 자동 플래시 권한을 결정하지 않는다

`boot`, `vendor_boot`, `init_boot`, `system`은 휘발성 작업 공간이 아닙니다. 업데이트는 부팅·데이터·복구 경로에 영향을 줄 수 있고, 허용 범위는 장치의 파티션·슬롯·잠금·서명 상태에 따라 달라집니다. ([Android 파티션 개요](https://source.android.com/docs/core/architecture/partitions))

| 작업 | 이 시리즈의 제안 정책 |
|---|---|
| 로그·식별 정보 읽기 | 데이터 접근 권한과 대상 확인 후 허용 |
| 재부팅·전원 제어 | 점유권과 작업별 사전 허용/승인, 복구 한도 확인 |
| 이미지 배포·플래시 | 기본은 사람 승인; 정책으로 사전 승인한 경우도 대상·해시·범위·만료 조건을 실행 시 검사 |
| 부트로더·파티션 구조 변경 | 일반 자동 수정 루프에서 제외하고 별도 검토된 절차 적용 |
| eFuse·키/RPMB 프로비저닝 | 이 파일럿의 자동화 범위에서 제외 |

승인 기록은 승인된 대상·산출물·행동·유효 범위와 연결합니다. 승인을 받은 뒤 이미지가 바뀌면 같은 승인으로 실행하지 않습니다. 문서의 “조심하라”는 문구보다 도구가 이 조건을 강제하는지가 중요합니다.

## 4. CI/Gerrit는 증거 보고부터 통합한다

초기에는 CI가 고정한 patchset을 대상으로 빌드·시험과 에이전트 분석을 수행하고, 외부 쓰기 없이 리포트를 생성하는 방식으로 검증할 수 있습니다. 다음에는 프로젝트가 승인한 서비스 계정과 권한 범위에서 코멘트·라벨을 연동합니다. 이 문서의 예시는 실제 Gerrit에 메시지를 전송하는 실행이 아닙니다.

1. 입력 patchset·manifest·Profile과 검증 정책 버전을 고정합니다.
2. 격리 환경에서 허용된 빌드·과제별 시험을 수행합니다.
3. 에이전트의 원인 후보·수정 제안과 검증자의 판정을 별도로 기록합니다.
4. 리포트에 실행 ID·검사 범위·미검증 범위·원본 증거를 첨부합니다.
5. 사전 승인된 피드백 정책이 있을 때만 코멘트나 CI 라벨을 게시합니다.

`Verified` 같은 라벨의 이름·점수·submit 요건은 프로젝트 설정에 따라 정합니다. 모델이 “문제가 없어 보인다”고 말한 것만으로 통과 라벨을 주지 않습니다. 최종 코드 반영은 프로젝트의 사람 리뷰·승인 규칙을 따릅니다. CI 연동 자체가 모든 BSP 업무의 자율 완료를 뜻하지는 않습니다.

## 5. 공통 KPI: 도입 첫날부터 같은 규칙으로 비교한다

이 절은 1~4편에서 사용하는 측정 규칙입니다. 마지막 단계에 도달한 뒤 측정을 시작하는 것이 아니라, 첫 호스트 파일럿부터 실행 기록을 수집합니다.

### 5.1 A/C 비교를 시작하고, 필요할 때 B를 추가한다

| 비교군 | 조건 |
|---|---|
| A: 현재 업무 방식 | 엔지니어의 기존 스크립트·검색·자동화·AI 도구와 검토 절차 포함 |
| B: 일반 코딩 에이전트 | C와 같은 모델·자원 한도·공통 작업 정보, BSP 전용 Skill·어댑터는 제외 |
| C: BSP 통합 흐름 | Profile·Skill·관측 어댑터·독립 검증·정책을 결합 |

A/C는 업무 개선 효과를, B/C는 BSP 전용 계약·도구를 추가한 효과를 조사합니다. B에도 같은 정답 판정 기준과 필수 안전 통제, 과제를 수행하는 데 필요한 정보는 제공합니다. 장치 제어 정책을 제거하는 실험을 하지는 않습니다. B/C에서 바뀐 요소를 명시하고, 개별 요소의 효과를 주장하려면 해당 요소만 바꾸는 추가 비교가 필요합니다.

과제 유형·난이도·빈도를 반영한 코퍼스를 정하고 개발용 사례와 미사용 평가 사례를 분리합니다. 실행 순서를 섞거나 담당자·사례를 배분해 정답을 먼저 본 효과를 줄이고 잔여 편향을 기록합니다. 모델·도구 버전, 자원 한도, cold/warm cache와 반복 조건도 남깁니다.

자동화 대상 여부(`eligible`)는 결과를 보기 전에 정합니다. 제외 과제와 이유를 함께 공개하며, 자동화 가능한 과제만의 성공률을 전체 BSP 업무 성과로 제시하지 않습니다.

### 5.2 완료·시간·품질·비용을 함께 보고한다

| 지표 | 계산·집계 규칙 |
|---|---|
| 검증된 완료율 | 사전 필수 검사와 독립 판정 기준을 충족한 실행 ÷ 전체 시도; 진단/수정 과제별 분리 |
| 무개입 자율 완료율 | 사람 조작·승인·수정 없이 검증 완료한 실행 ÷ 사전 정의된 대상 과제의 전체 시도 |
| 사람 투입시간 | 입력 준비·프롬프팅·조사·승인·검토·수정·인계 후 복구의 활성 시간 합 |
| 전체 경과시간 | 시작부터 최종 상태까지의 시간; 실패·시간 초과와 사람 인계 후 완료도 별도 추적 |
| 거짓 완료율 | 완료 보고 중 독립 검토·필수 시험에서 요구 조건 미충족이 확인된 건수 ÷ 완료 보고 건수 |
| 재작업·회귀율 | 정한 추적 기간 내 해당 변경에 귀속된 재작업·회귀가 확인된 완료 건수 ÷ 추적 가능한 완료 건수 |
| 업무 적용 범위 | 사전 정의한 자동화 대상 과제 수 ÷ 전체 접수 과제 수; 유형·빈도도 함께 보고 |

필수 승인만 받은 실행도 사람 조작이 있었으므로 무개입 자율 완료로 계산하지 않습니다. 대신 “승인만 필요”, “조사·수정 지원 필요”, “복구 필요”를 구분해 사람이 맡는 일이 어떻게 바뀌었는지 설명합니다.

독립 검사 통과는 그 검증 범위의 증거이며 거짓 완료를 완전히 배제하지 못합니다. 완료 보고가 없는 경우 거짓 완료율은 0%가 아니라 산출 불가로 표시합니다. 재작업 귀속이 불분명하거나 추적 기간이 끝나지 않은 사례도 분리합니다.

성공 사례만의 평균 시간으로 개선을 주장하지 않습니다. 실패·시간 초과·판정 불가·미완료를 포함한 수와 분모를 보고하고, 완료 사례의 시간 분포는 별도로 표시합니다. 표본 수·기간·반복 변동성을 함께 제시하고 데이터가 충분하면 중앙값·상위 지연 구간과 불확실성도 살펴봅니다.

CI 회귀 탐지는 알려진 회귀를 잡은 비율뿐 아니라 정상 변경을 잘못 차단한 비율도 측정합니다. 근거 없이 70% 해결·90% 차단·60% 절감을 공통 목표로 두지 않고, 기준선과 요구 품질에서 목표를 정합니다.

### 5.3 운영 비용과 구축 비용을 분리한다

```text
평가 기간 T, 비교 과제량 N을 먼저 고정한다.
운영 비용(T, N) = 사람 활성 시간 × 시간당 비용
               + 모델/API + 빌드/VM/장치 점유 + 별도 계측 비용
기간 순편익(T, N) = A 운영 비용(T, N) - C 운영 비용(T, N)
                 - T에 배분한 추가 구축·유지보수 비용
```

실패 후 복구·재작업 시간을 사람 시간에 넣었다면 같은 비용을 다시 더하지 않습니다. 공유 인프라의 배분 기준과 구축 비용의 배분 기간을 명시하고, 유지보수도 운영 비용 또는 별도 비용 중 한 곳에만 넣습니다. 품질 조건을 지킨 동일 과제량으로 비교하고, 시간 절감과 전체 비용 절감이 다르면 각각 보고합니다.

## 6. 확장 조건: 보드 수나 에이전트 수보다 병목을 본다

단일 에이전트와 명확한 Skill·도구로 시작할 수 있습니다. 병렬 조사나 독립 검토가 실제 병목을 줄일 때 다중 에이전트를 추가하고 같은 KPI로 비교합니다. 실물 DUT 운영과 다중 에이전트는 서로의 전제 조건이 아닙니다.

여러 에이전트를 쓰면 Lead가 범위를 배분하고, 각 작업자는 Profile·Observation·Artifact·Verification의 버전과 증거 경로를 전달합니다. 공유 소스·보드 변경은 소유권으로 제한하고 중복 실행·충돌·취합 비용을 기록합니다. 하드웨어 제어와 최종 검증은 에이전트의 역할 이름과 관계없이 실행 정책과 독립 검증자가 강제합니다.

확대 여부는 다음으로 판단합니다.

- 필수 품질·회귀·승인 조건을 유지했는가?
- 실패 후 복구까지 포함해 사람 시간이나 전체 경과시간이 개선됐는가?
- 추가 인프라·협업·유지보수 비용을 포함해 효과가 있는가?
- 더 넓은 과제군에서도 재현 가능한 결과인가?

확장한 범위에서 이 조건을 충족하지 못하면 원인을 좁히거나 범위를 줄입니다. 에이전트 수와 L번호를 높이는 것 자체를 완료 조건으로 삼지 않습니다.

## 시리즈를 적용한 뒤 남길 것

최종 산출물은 **대상 업무·기준선, 공통 계약, 호스트와 런타임 폐루프의 증거, 운영 정책, 비교 결과표와 남은 한계**입니다. 아직 실행하지 않은 설계는 설계로, 확인하지 못한 기능과 성과는 미검증으로 표시합니다.
