[3편]({{ '/posts/agentic-bsp-shift-phase1-strategy/' | relative_url }})에서는 호스트 업무의 폐루프를 만들었습니다. 런타임 작업에서는 여기에 **어떤 장치에서 무엇을 관측했으며, 어떤 시험으로 수정 효과를 확인했는가**가 추가됩니다.

Phase 2는 검증 범위를 런타임으로 확장하는 단계입니다. 모든 BSP 이슈가 가상 장치를 거쳐야 하거나, 가상 장치 통과가 실물 검증 완료를 의미하지는 않습니다. 아래 사례와 질의는 실행 절차를 설명하는 예시이며, 실제 측정 결과를 제시하는 것은 아닙니다.

## 1. 과제의 하드웨어 의존성으로 DUT를 선택한다

| 조사할 문제 | 출발할 환경 | 결과의 한계 |
|---|---|---|
| Android 공통 init·Framework·서비스 동작 | 해당 구성을 재현한 Cuttlefish | 제품별 HAL·주변장치 차이를 별도 확인 |
| 가상 보드가 지원하는 커널 기능·장치 드라이버 | 호환되는 QEMU 머신과 커널 설정 | 에뮬레이션되지 않은 SoC·주변장치는 검증 불가 |
| 실제 I2C 장치·PMIC·핀·전원·열·신호 문제 | 통제된 실물 DUT와 필요한 계측 | 해당 보드·환경·시험 조건에 한정 |
| 원인이 아직 불분명한 부팅 실패 | 기존 UART·dmesg·logcat부터 보존 | 환경을 바꾸기 전에 원래 증거와 재현성 확인 |

Cuttlefish는 Android Framework 동작을 높은 충실도로 재현하는 가상 장치입니다. 공식 문서는 물리 장치와의 주요 차이가 HAL 및 하드웨어 의존 소프트웨어에 있다고 설명합니다. 제품의 벤더 HAL과 드라이버가 그대로 동작한다는 보장은 없습니다. ([Cuttlefish 공식 문서](https://source.android.com/docs/devices/cuttlefish))

QEMU는 머신별 하드웨어 모델을 제공합니다. 일반적인 ARM64 `virt` 머신은 특정 제품 보드가 아니며, 실제 BSP 이미지를 그대로 부팅할 수 있는지 확인해야 합니다. 지원하지 않는 PMIC나 센서의 probe·전원 동작은 검증할 수 없습니다. ([QEMU ARM 머신 선택](https://www.qemu.org/docs/master/system/target-arm.html))

가상 DUT는 인스턴스별 상태를 분리하고 반복 실행하는 데 유용합니다. 자원 사용량, 기동·복구 시간, snapshot 지원과 초기 상태 재현 여부는 구성에서 측정합니다. 프로세스 종료만으로 디스크 상태까지 초기화됐다고 가정하지 않습니다. ([Cuttlefish snapshot/restore](https://source.android.com/docs/devices/cuttlefish/snapshot-restore))

## 2. 런타임 입력과 수집 계약을 고정한다

실행 전 Profile에 대상·이미지·필수 시험·관측 창·허용 동작을 등록합니다. 실물 장치를 바꾸는 실행은 5편의 점유·승인·복구 정책이 준비된 범위에서만 수행합니다.

```text
동일 입력과 환경에서 증상 재현
  ↓
원본 로그·trace와 장치/이미지/시간 기준 기록
  ↓
에이전트: 관측 사실을 찾고 경쟁 가설·다음 시험을 선택
  ↓
허용된 변경·배포 후 독립 검증자가 같은 시험 실행
  ├─ 요구 조건 충족: 변경 전후 증거와 검증 범위 보고
  ├─ 실패: 한도 안에서 다음 가설 검증
  └─ 증거 부족/복구 불가: INCONCLUSIVE 또는 인계
```

수집은 필요한 구간을 덮어야 합니다. ADB가 뜨기 전 문제는 UART·부트로더 로그·사용 가능한 이전 부팅 기록 등 별도 경로가 필요할 수 있습니다. Perfetto가 해당 사건을 수집하지 않았다면 SQL을 실행해도 그 사건은 나타나지 않습니다.

서로 다른 시계의 UART·kernel·Android 이벤트는 시간 정렬 방법과 오차를 기록합니다. 버퍼 손실·수집 실패·질의 출력 제한도 함께 남깁니다. 이벤트가 없다는 사실을 근거로 삼으려면 그 이벤트를 관측할 수 있는 수집 조건이었는지 먼저 확인합니다.

## 3. 예시: Android 서비스 기동 실패를 조사한다

설명용 증상은 “특정 서비스가 준비되지 않아 부팅 완료 조건을 충족하지 못한다”입니다. 서비스 이름·부팅 성공 조건·시간 창은 실제 과제의 계약에서 정합니다.

### 3.1 관측된 사실부터 찾는다

Android log가 수집된 trace에서는 실제 `android_logs` 테이블을 조회할 수 있습니다. 스키마와 사용 중인 Trace Processor 버전을 확인하고 필요한 시간 창·태그를 좁힙니다. ([Android log 데이터 소스와 SQL](https://perfetto.dev/docs/data-sources/android-log))

```sql
-- 수집된 Android log 중 오류 우선순위 이상의 일부 행을 조사한다.
-- LIMIT은 탐색용 질의 상한이며 CLI 출력 제한과 별도로 적용된다.
-- ts는 나노초 단위이며, 이 질의만으로 원인이 판정되지는 않는다.
SELECT ts, prio, tag, msg
FROM android_logs
WHERE prio >= 6
ORDER BY ts
LIMIT 100;
```

이 질의는 초기 탐색 예시입니다. 서비스 재시작과 SELinux 메시지가 모두 이 우선순위로 기록되는 것은 아니므로, 관련 원본과 다른 우선순위·태그도 조사해야 합니다. 결과 100행은 전체 기록이 아니며 출력 제한을 리포트에 표시합니다. CLI의 `--agent` 모드는 출력 형태와 크기를 조절하는 기능으로, 원인을 판정하는 기능은 아닙니다. ([CLI 문서](https://perfetto.dev/docs/reference/trace-processor-cli))

부팅 단계·재시작 횟수·denial 필드를 프로젝트별 테이블로 정규화할 수도 있습니다. 그 경우 입력 파서·뷰 정의·스키마 버전·원본 연결을 먼저 구현하고 검증해야 합니다. `boot_phases`, `android_services`, `selinux_denials`라는 이름의 표가 기본 제공된다고 가정하지 않습니다.

### 3.2 사실과 경쟁 가설을 나눈다

다음은 실제 결과가 아닌, 증거가 수집됐을 때 리포트를 작성하는 형식의 예입니다.

| 구분 | 기록 예시 |
|---|---|
| 사실 | 같은 부팅 세션에서 서비스 종료와 AVC denial이 관측됨; 원본 행·시각·장치 정보 연결 |
| 가설 A | 기대한 장치 노드 라벨과 실제 라벨이 달라 접근이 차단됨 |
| 가설 B | 서비스가 설계상 접근하면 안 되는 노드에 접근함 |
| 가설 C | 별도 초기화 실패가 있으며 denial은 동반 증상임 |
| 다음 확인 | 실제 노드·라벨·정책·접근 동작, 관련 종료 원인과 재현 시험 조사 |

AVC denial은 특정 접근과 SELinux context에 관한 증거입니다. 그 자체로 정책 추가가 정답이거나 Device Tree 오류라고 결론 내릴 수 없습니다. `permissive` 상태와 정책·라벨·프로그램 동작을 함께 확인합니다. ([Android SELinux 검증 문서](https://source.android.com/docs/security/features/selinux/validate))

### 3.3 원인을 구분할 시험과 수정 후 검증을 수행한다

원인 후보를 좁힐 수 있는 허용된 시험을 정하고, 수정 전 실패를 재현한 입력으로 수정 후 결과를 비교합니다. 서비스 준비 상태·해당 기능 시험·보안 정책 검사·영향 범위 회귀 검사를 과제에 맞게 선택합니다.

단순히 부팅 성공 마커가 생겼거나 denial이 사라졌다는 이유만으로 기능 완료를 선언하지 않습니다. 기능 비활성화·검사 삭제·보안 완화로 통과한 결과인지도 검토합니다. 증거가 충분하지 않으면 진단 결과를 가설과 다음 시험으로 마무리합니다.

## 4. 런타임 효과는 동일 조건의 반복 실행으로 측정한다

공통 KPI는 1편부터 수집한 실행 기록을 사용합니다. 런타임에서는 추가로 다음 조건을 고정합니다.

- 이미지·타깃·초기 데이터·콜드/웜 부팅·호스트 부하·수집 설정.
- 반복 횟수와 변동 범위, 성능 판정 기준 및 계측 오버헤드.
- 원인 규명의 정답 판정 절차와 판정자; 미해결 사례의 처리.
- 회귀를 놓친 비율과 정상 변경을 잘못 차단한 비율.

부팅 지연 기준을 500ms처럼 일괄 적용하지 않습니다. 제품 요구 조건과 반복 측정의 변동성을 보고 임계값을 정합니다. 진단 정확도·수정 완료율·처리시간은 다른 지표로 보고하며 고정된 절감률을 측정 없이 성과로 제시하지 않습니다.

## 이 편의 산출물과 다음 확장

산출물은 **DUT 적용 범위표, 재현 절차, 원본 관측 자료, 사실·가설·시험 기록, 독립 검증 결과와 기준선 비교**입니다. 가상 DUT 결과는 가상 환경에서 실제로 확인한 범위로 표시합니다.
